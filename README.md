# AutoClicker · Windows 10 自动点击器

[![Windows 验证](https://github.com/jimmy-yao/autoClicker/actions/workflows/windows.yml/badge.svg)](https://github.com/jimmy-yao/autoClicker/actions/workflows/windows.yml)

基于 **Python 3 + PySide6** 的桌面自动化工具，输入注入走 Win32 `SendInput` / `PostMessage`，
另有基于 **UI Automation** 的「按控件点击」后端；三种方式都不依赖任何第三方输入库。

当前版本：**P5** — 在 P4 的后台点击之上加了 **UIA 无障碍输入后端**：按坐标取到「控件」，再调用它的
`InvokePattern.Invoke()`。不移动鼠标、不抢焦点，网页控件（Chromium / JCEF / Electron）也能点。

- **P4** — 后台点击：用 `PostMessage` 把点击直接投给目标窗口，不移动系统光标。
- **P3** — 找图：等屏幕上出现某张图片再继续。
- **P2** — 录制回放。
- **P1 / P0** — 步骤序列、方案管理、热键、托盘、单实例、DPI。

> 📖 面向使用者的操作说明见 [`docs/USAGE.md`](docs/USAGE.md)。

## 运行

```powershell
python main.py
```

### 快速上手

1. **新建一个点击步骤**：点「+ 点击」。
2. **设定坐标**：在对话框里点「拾取坐标 (F8)」，屏幕变暗后移动鼠标到目标位置，**左键**确认。
   （对话框会先自动隐藏，拾取完再弹回来。也可以直接在主窗口选中某一行后按 F8 改写坐标。）
3. **继续加步骤**：比如再加一个「+ 延时」等页面加载，再加一个「+ 按键」。
4. 需要的话勾掉某几步的「启用」列，临时跳过它们。
5. 设置**序列轮数**（填 `0` 为无限）和**启动延迟**（留出切窗口的余量）。
6. 按 **F9** 开始（窗口会自动最小化），**F10** 停止。
7. 需要**不占用鼠标**、或目标窗口不能拿到前台时，把「**输入方式**」换成
   「后台点击（PostMessage，不占鼠标）」或「UIA 无障碍（按控件点击，不移动鼠标）」——两者能力与
   限制见下文对应两节。拿不准哪个能用，就直接跑一次探针（见下文），它会给出结论。

> ⚠️ 默认的 `SendInput` 是前台注入，会真实移动系统光标并产生真实点击，运行期间**不要移动鼠标**；
> 换成后两种就不再占用鼠标，但适用面更窄（`PostMessage` 只对认 `WM_*` 的经典 Win32 窗口有效，
> UIA 要求目标暴露无障碍树），建议**先探针、再上宏**。

### 录制回放

不用一个个手搭步骤，直接录一遍：

1. 点「录制 (F11)」（或直接按 **F11**）。主窗口会让开，屏幕顶部出现「● 录制中」指示条。
2. 正常操作鼠标键盘。指示条会实时显示已录到的「点击/按键」数与「移动采样」数。
3. 按 **F10** 结束录制。
4. 弹窗让你选：**替换当前步骤** / **追加到末尾** / **丢弃**。
5. 内容进步骤表后可以直接编辑、调时长、调顺序，再按 F9 回放。

录完之后想微调坐标，不用重录：选中那一行按 **F8** 即可。点击步骤改的是落点坐标，
移动步骤改的是**终点**（起点保留、中间拐点拉直）。

录制会自动做三件「整理」工作，所以结果通常比想象中干净：

- **连点合并**：同一个点连点 5 下 → 一个「点击 ×5，间隔 150ms」的步骤，而不是 5 行；
- **连按合并**：同一个键重复按 → 一个「按键 ×N」；
- **轨迹压缩**：一整段鼠标移动 → **一个**「移动」步骤（内部存折线拐点 + 总时长），
  默认抽稀到 12px / 80ms 一个点，2px 以内的手抖直接丢掉。

两个可选开关（都在录制按钮右边）：

| 开关 | 默认 | 作用 |
|---|---|---|
| 记录鼠标移动 | 开 | 关掉后只录点击和按键，步骤更精简。开着才能还原「移到菜单上再点」这类悬停操作。 |
| 屏蔽输入 | 关 | 勾上后录制期间鼠标键盘**不会传给任何程序**，纯空录坐标和节奏，绝不会误点。代价是「点开菜单→再点菜单项」这种有依赖的流程录不出来（因为菜单根本不会打开）。 |

> 「屏蔽输入」勾上时 F10 是**唯一**的结束方式，因此本工具会先确认 F10 热键注册成功才允许开录，
> 避免把你自己锁在一个点不动的系统里。不勾选时 F10 依然是最方便的结束方式，但托盘菜单也能结束。

录制期间不记录「工具自己的控制键」（F8/F9/F10/F11），也不会记录其它程序注入的事件
（`LLMHF_INJECTED` / `LLKHF_INJECTED`），所以不会把回放动作又录一遍。

### 找图（等某个东西出现）

「录制」只能记下「什么时候做了什么」，记不下「等某个按钮出现再点」。要找图步骤来补：

1. 点「**+ 找图**」，对话框里点「**截取屏幕**」。
2. 屏幕会压暗，**左键拖一个框**框住要认的目标（比如那个「继续」按钮），松手即完成截取。
   框太小会被当成误触，直接重拖一次即可；右键或 Esc 取消。
3. 回到对话框，上方会显示模板预览图和尺寸，并提示这块画面「含多少像素的纯色区域」。
   出现**橙色警告**说明这块画面没有纯色底色，匹配只能逐像素硬碰，建议把按钮的底色一起框进来。
4. 调参数（一般默认值就够）：

   | 字段 | 说明 |
   |---|---|
   | 容差 | 抽样比对时每个像素通道允许的色差，默认 32。主要用于容忍文字抗锯齿。 |
   | 超时 | 最多等多久，默认 30 秒。填 `0` 表示只找一次，找不到立刻按「超时后」处理。 |
   | 轮询间隔 | 每隔多久看屏幕一眼，默认 300ms。每看一眼都要抓一帧整屏，间隔越大越省 CPU。 |
   | 找到后点击它 | 勾上就点一下模板中心（可加偏移、可换按键）；不勾就只「等它出现」。 |
   | 超时后 | 「继续下一步」或「停止并报错」。 |

5. 点「**模拟测试**」可以不跑宏、不点鼠标，就地抓一帧看看现在能不能找到——调容差时非常省事。
   （测试时对话框会先自动隐藏，否则找图会先命中对话框里的模板预览图。）

> 找不到时会话框会告诉你「是颜色完全没对上」还是「有几处颜色接近但形状不对」，
> 这两种情况的处理方式完全不同：前者基本是目标没显示或界面变了，后者才值得调容差。

### 后台点击（不占用鼠标）

默认的点击走 `SendInput`，是**前台注入**：它真实移动系统光标，所以运行期间不能动鼠标，
目标窗口也必须在前台。把主窗口的「**输入方式**」换成「**后台点击（PostMessage，不占鼠标）**」后会改用它：

- 点击变成**往目标窗口的消息队列投递** `WM_MOUSEMOVE` / `WM_LBUTTONDOWN` / `WM_LBUTTONUP`；
- **不移动系统光标**，宏跑着的时候你照样能用鼠标；
- **不要求目标窗口在前台**，部分被遮挡也能点（前提是能拿到它的窗口句柄 HWND）。

后台点击需要一个**目标窗口**，用于把屏幕坐标换算成该窗口的**客户区坐标**。两种给法：

1. **绑定窗口**（推荐）：点「绑定窗口」，屏幕压暗后**点一下目标窗口**，就把它定为目标。
   之后所有点击都投给它——哪怕它被别的窗口挡在前面。未绑定时会退化成第 2 种。
2. **不绑定**：每次点击时用 `WindowFromPoint` 找该屏幕坐标处**当时最顶层**的窗口来投递。
   省事，但目标被盖住时会投错对象。

命中目标不是顶尖层窗口，而是**该点下最内层的子窗口**——真实鼠标消息正是由命中测试路由到
那一层的，只丢给顶层窗口很多程序不会自己再往下转发。点击前还会先补一条 `WM_MOUSEMOVE`，
因为不少控件靠它更新悬停/热点状态。

> ⚠️ **后台点击的适用面比前台窄**，这是 `PostMessage` 机制的固有局限，不是 bug：
>
> - 只对**自己处理鼠标消息**的经典 Win32 窗口有效。Chromium/Electron（大部分新版应用
>   和浏览器）、DirectX 游戏、不少 UWP 会**直接忽略**投递进来的消息，表现为「点了没反应」；
> - 不会产生 `WM_ACTIVATE` / 焦点变化，个别控件要先获得焦点才响应；
> - **发送方与目标进程的权限级别要匹配**：Windows 的 UIPI 会拦掉低权限进程发往高权限进程的
>   消息（比如本工具没提权、目标程序是管理员运行），表现为投递失败或没反应；
> - **键盘消息**只能投给绑定窗口（没绑定就退而求其次给前台窗口），后台键盘比后台鼠标更不可靠；
> - 换台机器、目标程序重新开过之后 HWND 会失效，届时会**自动退回**按坐标识别窗口兜底。
>
> 一句话：**能前台就用前台**；只有当「不能占用鼠标 / 目标窗口不能拿到前台」时，才值得
> 赌一把后台，且优先手动绑定窗口。

**换目标程序前先自检。** `PostMessage` 能不能用，完全取决于目标程序认不认 `WM_*` 消息，
所以给新程序（尤其是 Java、内嵌网页的程序）配后台点击之前，先跑一次探针：

```powershell
python tools\probe_background.py
```

它**自己给结论**，不需要你去读窗口类名：跑一次会打印「路线 + 置信度 + 理由 +
可直接照抄的方案」，并顺手把模板截好填进方案里（会把光标从按钮上挪开再截，避免拿到悬停态）：

- 路线是**后台点击** → 照它给的步骤把输入方式选成「后台点击（PostMessage，不占鼠标）」+ 绑定窗口就能跑；
- 路线是 **UIA** → 说明 `WM_*` 这条路对你不通，但 UIA 走得通，输入方式选
  「UIA 无障碍（按控件点击，不移动鼠标）」即可；
- 路线是**前台** → 判不出来时的保守选择，前台一定有效，只是会占用鼠标。

它还会**实测给你看**：先真投一记后台点击比对像素，没变化就再**真 Invoke 一记 UIA** 比对一次
（用的是界面里那个 UIA 后端同一份代码，所以探针说什么、跑起来就是什么）。
加 `--save 继续续跑` 可以直接把方案写进 `%LOCALAPPDATA%\AutoClicker\profiles\`，不用手抄 JSON。
判定依据与优先级见「技术要点 · 14」。

### UIA 无障碍点击（不移动鼠标）

`PostMessage` 那条路对**网页控件**（Chromium / Electron / JCEF，以及 IDEA 里内嵌的网页）
一定走不通——消息投进去会被渲染器丢掉。这类界面还有一条「中路」：**UI Automation**。

UIA 不看像素、也不投消息，而是**按控件办事**：拿坐标去问系统「这里是哪个控件」，
再让那个控件执行它自己的「被点击」语义（`InvokePattern.Invoke()`）。

- **不移动系统光标**，宏跑着的时候你照样能用鼠标；
- **不抢焦点**，目标窗口不必在前台，被挡在后面也行；
- 找图依然负责**「在哪儿」**（像素定位），UIA 只负责**「怎么按下去」**——两者是搭配关系。

同样需要一个**目标窗口**（用于把屏幕坐标定位到控件上）。UIA 模式下「绑定窗口」的含义变了，
它不再是「往哪儿投消息」，而是**安全校验**：

> `ElementFromPoint` 是按**屏幕坐标**取控件的，如果目标被别的窗口**挡在下面**，取到的会是
> **遮挡它的那个窗口的控件**。绑定窗口之后，取到的控件只要不属于绑定的进程，就**跳过这一跳
> 并在日志里告警**——宁可漏点一次，也不要误点别人。没绑定时不做这层校验。

> ⚠️ **UIA 的适用面同样是有限的**，这是无障碍树的固有约束，不是 bug：
>
> - 目标程序**必须暴露无障碍树**。Swing/AWT 程序（含 IDEA）要开 Java Access Bridge
>   （`jabswitch -enable`）**并且**开 IDEA 的 `Settings → Appearance & Behavior → Appearance →
>   Support screen readers`（改完要**重启 IDEA**）；Chromium/Electron 多数情况下默认就有。
> - **只有「有 Invoke 语义」的控件能点**：按钮、链接、菜单项、列表项可以；纯文本、空白区域不行。
>   取到的常是按钮**里面的文本节点**，所以后端会自动**往上找几层祖先**，找到第一个能 Invoke
>   的控件再点（默认最多上溯 3 层）。
> - **右键 / 中键、移动鼠标、按键在 UIA 里没有对应语义**，这三种操作会**回落到前台注入**
>   （日志里会提示一次）。也就是说：UIA 模式保证的是**左键点击不占鼠标**，
>   不是「整个宏绝对不碰鼠标」。
> - 跨完整性等级同样受 UIPI 限制（没提权就点不到管理员程序里的控件）。

一句话：**能前台就前台；不能占用鼠标时，先探针——它会在「后台点击」和「UIA」之间给你答案。**

### 热键

| 键 | 作用 |
|---|---|
| F9 | 开始回放 |
| F10 | 停止回放 / 结束录制 |
| F8 | 拾取坐标（编辑对话框开着时由对话框接管） |

## 数据存放位置

```
%LOCALAPPDATA%\AutoClicker\
├─ settings.json              # 最近使用的方案
├─ profiles\
│  └─ 默认方案.json
├─ shots\
│  └─ 找图失败-20261017-153012.png   # 找图超时中止时的现场截图，只留最近 10 张
└─ logs\
   └─ autoclicker.log         # 滚动保留，最多 3 个备份
```

方案文件是纯 JSON，可以直接手改、备份或分享。找图步骤的模板是**自带**的
（`base64(magic + 宽高 + zlib 压缩的 BGRA)`），所以方案文件可以直接换台机器用，
不需要额外的图片文件：

```jsonc
{
  "version": 1,
  "name": "默认方案",
  "repeat": 0,                 // 整个序列重复轮数，0 = 无限
  "repeat_delay_ms": 0,        // 每轮之间的间隔
  "start_delay_ms": 300,       // 按开始后的等待时间
  "steps": [
    { "kind": "click", "enabled": true, "x": 960, "y": 540, "button": "left",
      "repeat": 10, "interval_ms": 200, "jitter_ms": 0, "jitter_px": 0, "note": "" },
    { "kind": "delay", "enabled": true, "delay_ms": 1500, "jitter_ms": 200, "note": "等加载" },
    { "kind": "wait",  "enabled": true, "template": "QUNUMXgAeAD...", "tolerance": 32,
      "timeout_ms": 30000, "poll_interval_ms": 300, "click": true, "button": "left",
      "offset_x": 0, "offset_y": 0, "on_timeout": "continue", "note": "等「继续」弹窗" },
    { "kind": "move",  "enabled": true, "points": [[100, 200], [180, 205], [300, 260]],
      "duration_ms": 420, "note": "划过去再点" },
    { "kind": "key",   "enabled": true, "vk": 116, "repeat": 1, "interval_ms": 50, "note": "F5 刷新" }
  ]
}
```

写入采用「临时文件 + `os.replace`」的原子替换，中途崩溃不会留下半个文件。
单个步骤损坏只会被跳过并记日志，不会让整个方案打不开。

## 技术要点

### 1. 输入注入：SendInput（前台）

用 `ctypes` 直接调用 `user32.SendInput`，一次调用原子地发送「移动 + 按下 + 抬起」。

坐标使用 `MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK`，把虚拟屏幕物理像素
归一化到 `0..65535`，可以正确处理多显示器与负坐标。

结构体布局是关键：`INPUT` 在 x64 上是 **40 字节**（`ULONG_PTR` 8 字节 + 8 字节对齐），
算错会导致 `SendInput` 返回 0 且没有任何报错。测试里有断言守住这一点，也守住了
`mi` / `ki` / `hi` 共享内存这一语义。

### 2. DPI 感知

入口第一件事就是 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`，
必须在创建窗口之前。否则 Windows 会对坐标做虚拟化，点击位置出现比例偏移。

### 3. 线程模型

```
主线程 (UI)                      工作线程
  MainWindow                       MacroEngine
     │  start_requested ──────────▶  run(profile)      ← 队列连接投递
     │  ◀── started / step_changed / progress /
     │      stopped / failed                            ← 队列连接回传
     │  request_stop() ────────────▶  stop_event.set()  ← threading.Event，跨线程安全
```

`MacroEngine` 通过 `moveToThread` 搬到工作线程，UI 线程绝不 `sleep`。
进度信号按 50ms 节流，避免 1ms 间隔时把事件循环淹掉。

### 4. 时序精度

用 `perf_counter()` 单调时钟维护**下一个绝对触发时刻**，每轮只 sleep 差值，
不会像 `sleep(interval)` 那样累积漂移；落后过多时重置时间轴，避免「追赶风暴」。

**所有等待**（启动延迟、步骤间隔、延时步骤、轮次间隔）都走 `Event.wait()` 而不是 `sleep()`，
所以 F10 能立刻打断——哪怕正卡在一个 5 秒的延时步骤里。测试覆盖了这一点。

### 5. 全局热键

`RegisterHotKey` + `QAbstractNativeEventFilter` 拦截 `WM_HOTKEY`。

**刻意不用键盘钩子来做热键**：钩子需要常驻拦截全局按键流，更容易被安全软件误报。
钩子只在**录制期间**临时安装，录完立刻摘掉（见下一节）。

### 6. 录制：低级钩子（仅录制期间安装）

用 `SetWindowsHookEx` 的 `WH_MOUSE_LL` + `WH_KEYBOARD_LL`，而不是：

- `WH_JOURNALRECORD`：Vista 之后对非提权进程基本失效，已废弃；
- `GetAsyncKeyState` 轮询：拿不到精确时序，也无法屏蔽事件；
- `pynput` / `keyboard` 之类第三方库：底层还是同一套钩子，白白多一层依赖。

低级钩子**不注入其它进程**，回调是在「安装钩子的那个线程」上通过消息队列调用的，
所以不需要写 DLL，Qt 主线程自带消息循环。代价是三条硬约束：

1. **回调必须极快**。Windows 有 `LowLevelHooksTimeout`（默认 300ms），超时会被系统静默摘掉钩子。
   因此回调里只做「追加一条记录」，绝不做 IO、UI 或加锁。
2. **必须忽略注入事件**（`LLMHF_INJECTED` / `LLKHF_INJECTED`），否则会录到自己的回放，
   也可能和其它自动化工具互相打架。
3. **必须持有 `HOOKPROC` 的引用**。回调是 ctypes 闭包，被 GC 掉以后系统回调到野指针会直接崩进程。

事件到步骤的转换分三段，每段都能单独测试：

```
原始事件 ──①收敛──▶ 动作 ──②合并──▶ 动作组 ──③补延时──▶ 步骤
         按下/抬起配对         连点→repeat        按真实间隔插 DelayStep
         移动采样→折线         连按→repeat
```

**「一个移动 = 一个步骤」**：录一分钟鼠标会产生上万条 `WM_MOUSEMOVE`。如果逐点成步，步骤表会直接
爆炸。这里把一整段连续移动抽稀成一条折线（默认 12px / 80ms 一个拐点）加上总时长，
回放时再按「各段长度比例分配总时长」匀速插值——拐点疏密不同也不会忽快忽慢。

### 7. 坐标拾取器与模态对话框

取点经常发生在「某个窗口正开着」的时候，而这些窗口往往正好挡住要拾取的位置。
`PickCoordinator` 把「先隐藏请求方 → 显示遮罩 → 回调 → 再恢复请求方」收在一处。

为什么要**隐藏**请求方而不是仅靠遮罩盖在上面：Qt 的**模态**对话框会拦截其它窗口的输入，
而隐藏的模态窗口不参与输入拦截，遮罩才能正常接到鼠标点击。

**但「隐藏请求方」会撞上 Qt 的一处语义陷阱**：`QDialog::setVisible(false)` 会主动退出
`exec()` 起的模态循环（qdialog.cpp 里的原话：「Reimplemented to exit a modal event loop
when the dialog is hidden」）。步骤编辑对话框正好是 `exec()` 打开的，而它上面的
「拾取坐标 / 截取屏幕 / 模拟测试」三个按钮都要先把自己 `hide()` 掉让开——用 `exec()` 的话，
**点一下就等于按了取消**：`exec()` 立刻返回 `Rejected`，这一步被丢掉；等用户拖完框，
对话框又因为只剩拾取器一个引用、引用一断就被销毁，表现成「窗口自己关掉了」。

所以 `StepEditor._open_dialog` 不用 `exec()`，而是自己起一个 `QEventLoop`，只在真正的
accept / reject（`finished`）时退出，中间被 `hide()` / `show()` 多少次都不受影响；
另接一个 `destroyed` 兜底，免得对话框在流程中被销毁时这个循环永远挂着。

同一处还有个不变式：**抓屏失败也必须把请求方还回去**。`_capture_template` /
`_capture_full` 里的 `_restore()` 写在 `finally` 里——漏掉它的症状是「窗口再也回不来，
而且此后所有拾取都被 `busy` 挡回去」，比抓屏失败本身难查得多。

### 8. 坐标拾取器的双坐标系

- **视觉布局**用 Qt 逻辑坐标（所有 `QScreen.geometry()` 的并集），保证多显示器时贴合；
- **实际捕获**用 Win32 `GetCursorPos()` 物理坐标，保证与 `SendInput` 同一坐标系。

### 9. 找图：零依赖的模板匹配

`cv2.matchTemplate` 是标准答案，但 OpenCV 会给 exe 塞进 40MB+ 的依赖，而这个项目一直
守着「只有 PySide6」的线。这里换一套借用 `bytes.find()` 的做法：

```
模板 ──▶ 挑 1~2 条「像素签名」 ──▶ 在整帧裸字节上 find() ──▶ 候选位置
                                        （C 层 memmem）          │
                                                                 ▼
                                              8x8 抽样点做容差比对，排除假命中
```

关键在于**签名要长、要稀有**，这样绝大多数字节位置在第一步就被 C 代码否掉，
真正进 Python 循环的候选只有个位数（实测：3456×1080 的一帧，找图 1~6ms）。

签名挑两条，**先锐利、后退让**：

1. **内容最丰富的那一行**整行像素（横跨文字和边框）——签名里带着颜色变化，
   几乎不会在别处误命中；代价是要求这一整行逐像素一致。
2. **最长的一段纯色横线**——纯色几乎不可能渲染出差异，所以最稳，是 1 号整条落空时的退路；
   但它太「普通」，在大面积同色背景上会产生一大堆候选。

两个坑值得单独说：

- **搜索区间必须裁到「模板左上角的合法范围」里**。整块同色的桌面上，签名会在每一行都命中，
  不裁的话前几千个候选全是越界的废命中，配额烧光了才发现真答案在屏幕中间——
  这个 bug 就是真机联调时才暴露的（离屏测试的合成屏幕太干净，照不出来）。
- **签名是逐字节比对的，不做模糊搜索**。「容差」只作用于最后那步抽样比对，
  用来容忍文字抗锯齿一类的细微差异，救不回整体变色。所以目标程序换主题 / 换语言 /
  改 DPI 缩放后必须重新截模板——这是刻意的取舍，换来的是零依赖 + 每帧几毫秒。

### 10. 抓屏：GDI BitBlt

`BitBlt`（屏幕 DC → 兼容 DC）+ `GetDIBits`（取回裸像素），拿到**自顶向下 32 位 BGRA**。
一次全虚拟桌面抓屏（本机 3456×1080）约 50ms，是轮询里的大头；默认 300ms 轮询下
大约占一个核的 15%。GDI 句柄在 `finally` 里成对释放。

`ScreenFrame` 带自己的 `x/y` 原点，所以找图算出来的坐标加上帧原点就是**屏幕绝对坐标**，
副屏负坐标（本机虚拟桌面原点就是 `-1920`）不需要任何特判。

### 11. 截模板：为什么要「隐藏 → 等 150ms → 再抓」

拖框遮罩是半透明压暗的，如果松手当场抓屏，会把遮罩自己也拍进模板里。
所以流程是：**遮罩先彻底隐藏 → 等 `HIDE_SETTLE_MS`（150ms）让 DWM 重绘完 → 再抓那一块**。

「模拟测试」同理：对话框里正显示着模板预览图，而预览图**就是模板本身**，
不先让开的话找图会先命中自己的预览图，测出来的结果毫无意义。

另外 `PickCoordinator.busy` 不能只看遮罩可见性——松手之后遮罩已经隐藏、截取还没完成，
这一小段窗口期里必须继续拒绝新的取点请求（比如用户又按了一下 F8）。

### 12. 后台注入：PostMessage

前台注入（`SendInput`）驱动的是唯一那一个系统光标，所以「不占用鼠标」这条需求在它身上无解；
后台注入必须换成 `PostMessageW`，往目标窗口的消息队列里投递鼠标/键盘消息。

两个实现要点：

- **坐标换算成客户区坐标**。`WM_LBUTTONDOWN` 的 `lParam` 是相对**目标窗口客户区**的坐标，
  而本项目内部一律是虚拟屏幕物理像素，所以要先 `ScreenToClient`。
- **投给该点下最内层的子窗口**。真实鼠标消息由系统命中测试路由到最内层控件；投递的消息
  没有这层路由，只发给顶层窗口的话，很多程序的 `WndProc` 并不会自己再往下转发，于是
  「点了没反应」。这里用 `ChildWindowFromPointEx` 逐层下钻（默认跳过不可见与
  `WS_EX_TRANSPARENT` 的子窗口，因为真实鼠标会直接穿过它们）。

后端是可插拔的：`MacroEngine` 只依赖 `InputBackend` 抽象接口（`app/input/base.py`），
前台 / 后台 / UIA 只是三个实现，引擎与步骤模型一行都不用改。引擎在 `start` 之前用 `set_backend()`
接收当前选择，运行途中禁止切换，避免同一次运行混用多种注入方式。
「只提示一次」这类状态由 `reset_notices()` 在每次运行开始时清掉，所以每个方案都会重新提示一遍。

### 13. PostMessage 不是万能的：三条备选路

「后台点击」这个词容易让人以为存在一个通吃所有程序的开关，其实**能不能后台点，取决于目标
程序认不认 `WM_*` 消息**，而这是分阵营的：

| 目标类型 | `PostMessage` | 说明 |
|---|---|---|
| 经典 Win32 / MFC / duilib | ✅ | 消息模拟的舒适区 |
| Qt / Swing(AWT) | ✅ 通常可以 | AWT 的窗口过程由 Java 处理，会把 `WM_*` 翻译成 Java 鼠标事件 |
| Chromium / Electron / JCEF | ❌ | 输入不走 `WM_*`，投进去也不产生真正的点击 |
| DirectX / 部分 UWP | ❌ | 绕过标准输入队列 |

所以「有人的自动点击工具后台点得很好」往往是**目标程序恰好是能收消息的那一类**，而不是工具更强。
真正通吃现代程序的后台方案只有两条，各有代价：

1. **UI Automation（无障碍接口）** —— 通过 Windows 的 UIA 树拿到「继续」这个**控件对象**，
   调用 `Invoke()`。不移动光标、不需要前台、不怕换主题/DPI。代价是**要求目标程序暴露无障碍树**：
   Swing 需要开 Java Access Bridge + IDEA 的「Support screen readers」，Chromium 需要 a11y 被激活。
   **本项目 P5 已实现这条路**（输入方式里选「UIA 无障碍」），实现见下一条。
2. **进程注入 / 挂钩**（大漠插件的 `dx` 模式、各种「后台键鼠」驱动走的就是这条）—— 把 DLL 注入
   目标进程，挂钩它的消息循环 / DirectX / 输入管线。**什么程序都能点**（包括游戏），但极易被
   杀软 / 反作弊判定为恶意，每个程序要单独适配、随目标升级失效。本项目**刻意不做**这条路。

还有一条是「伪后台」：保存光标 → `SetCursorPos` + `SendInput` 点击 → 还原光标。看着几乎不打扰，
但只要光标和焦点被抢走，你就没法同时用别的窗口——它不是真正的后台。

**先自检，再决定。** `tools/probe_background.py` 把上面这张表落到你的具体程序上：
它自己给结论（三条路里选一条 + 置信度 + 理由）、实测哪条真的生效，并顺手生成能直接用的方案。
判定怎么做到的，见下一条。

### 14. 探针怎么「自动判断」：几路证据按可信度合议

探针不靠猜，把证据按可信度排了个序，先命中的说了算：

| 优先级 | 证据 | 为什么可信 |
|---|---|---|
| 1 | **窗口链里有 Chromium/CEF** | 决定性判据。有它 → 这个按钮是网页画的，`WM_*` 一定被渲染器丢掉，**与外面套的是 Swing 还是 Qt 无关**。它**比「实测有变化」还硬**：网页里焦点/悬停的副作用同样会让画面变 |
| 2 | **框架类名** | `SunAwt*` / `Qt*` / `WindowsForms*` / `HwndWrapper*` 通常认 `WM_*`；`ApplicationFrameWindow`(UWP) / WinUI 不认。明确说不认的直接改判 |
| 3 | **实测后台投递**：真投一记 `WM_LBUTTONDOWN/UP`，比对前后那块屏幕的像素 | 唯一的直接经验证据。「有变化」是强证据，「没变化」只是弱证据（按钮按下可能只闪一下） |
| 4 | **实测 UIA Invoke**：真调一次 `Invoke()`，同样比对像素 | 后台没反应时用它判断「中路」通不通。`Invoke` 返回成功只能说明调用没报错，所以照样要看像素 |
| 5 | **UIA 结构**：坐标下的控件（或其祖先）支不支持 `InvokePattern` | 决定「要不要再花一次点击去试中路」，也决定 UIA 模式跑起来会不会有点不到的地方 |

两个刻意的设计：

- **Chromium 优先于其它一切**。IDEA 主窗口类是 `SunAwtFrame`（Swing，看着很乐观），
  但 JCEF 面板的按钮实际由 `Chrome_RenderWidgetHostHWND` 画——只按顶层类名判会得出完全相反的
  结论。所以窗口链里只要有 Chromium，就直接改判，实测「有变化」也不翻盘。
- **测之前先确认那块区域自己不会变**。点击前连拍两帧比对，不一致就说明那里有动画/光标闪烁，
  实测结果标为「不可信」，退回按结构判定 —— 免得把动画当成「点击生效了」。

判不出来时（既没识别出框架、也没实测）给的是**前台**，不是后台：前台 `SendInput` 一定有效，
是唯一安全的默认。宁可推荐一条笨但能用的路，也不推一条可能白折腾的路。

**UIA 那一节用的是本项目自己的实现**（`app/win/uia.py` + `app/input/uia.py`），不是第三方
`uiautomation` 库——探针与界面里选 UIA 模式走的是**同一份代码**，所以探针说什么、跑起来就是什么。

### 15. UIA 后端：为什么手写 COM，而不是装个现成的库

做 UIA 最省事的办法是 `pip install uiautomation`（或 `comtypes`），但它会打破本项目的
一条底线：**运行期只依赖 PySide6 + 标准库**（`requirements.txt` 里只有一行，`build.bat`
打出来的 exe 才那么小）。所以这里用 `ctypes` **手写最小的 COM 面**。

COM 在 Python 里的麻烦之处在于**虚表下标**：`IUIAutomation` 的方法只能靠「函数指针表里第几个」
调用，而**下标错一个数不会报错，只会静默调到隔壁函数上**，甚至直接让进程崩掉。做法是：

- 只取真正要用的几个方法，一张表钉死（`app/win/uia.py` 的 `VTABLE`）：
  `IUIAutomation.ElementFromPoint` / `ControlViewWalker`、
  `IUIAutomationElement.GetCurrentPattern` 与几个 `Current*` 属性、
  `IUIAutomationTreeWalker.GetParentElement`、`IUIAutomationInvokePattern.Invoke`。
- 下标不是猜的：从微软官方 `UIAutomationClient.idl` 的**声明顺序**推出来，并由
  `tests/test_uia.py` 把**整张表**逐条钉住（改一个数就红）。
- 光有单测还不够——单测只能证明「表和它自己一致」。所以 `test_uia.py` 里还有一组
  **真 COM 自检**（`TestRealUia`，只在 Windows 上跑，CI 的集成 job 会执行）：在真实桌面上
  走一遍 `CoCreateInstance → ElementFromPoint → 读 Current* 属性 → GetParentElement →
  GetCurrentPattern`，把整条链真的调一次。这是唯一能证明下标没写错的办法。
- **调用层本身也被端到端测了**。手写 COM 的失败模式不是抛异常，而是**段错误**——
  最典型的是「解引用几层」写错：COM 对象的第一个字段才是虚表指针，少解一层就会把虚表指针
  当成函数地址（实测读出来是 `0xfd010303` 这种垃圾，一调就崩），而且**根本不报错**。
  所以 `test_uia.py` 会现造一个假 COM 对象、往虚表里塞**真回调**，把 `_call` 真的调起来、
  验参数与返回值、验出参指针的收发。这也顺带说明了一件事：这类代码「看起来对」没有意义，
  只有真的调用过才算数。

另外几个刻意的设计：

- **COM 只在引擎线程里碰**。`IUIAutomation` 有线程亲和性（必须 `CoInitializeEx` 过才能用），
  所以客户端用 `threading.local` 按线程惰性创建，挂在引擎的工作线程上；界面线程不碰它。
- **每个指针都要还**。`Element` 用完即 `Release`，自动往上找祖先的那个循环里每换一层就把
  上一层放掉——`Release` 漏一次就是一个 UIA 进程里的常驻泄漏。
- **找不到就告警，不擅自换路**。坐标下的控件和它的祖先都不支持 `InvokePattern` 时只记一条
  WARNING，**不会**偷偷改回前台点击——那样宏的行为会随界面状态漂移，比漏点一次更难查。
- **UIA 里没有语义的操作显式回落**：右键/中键、移动鼠标、按键回落到前台 `SendInput`
  后端（`UiaBackend(fallback=...)`），并**每次运行提示一次**。契约是「左键点击不占鼠标」，
  不是「整个宏绝对不碰鼠标」。

## 已知限制（技术边界，不是 bug）

1. **前台注入会占用鼠标**：默认的 `SendInput` 点击作用于光标所在位置的窗口，运行期间不能移动鼠标。
   需要「不占用鼠标」时把输入方式换成「后台点击（PostMessage）」或「UIA 无障碍」——前者只对处理
   `WM_*` 消息的经典 Win32 窗口有效，后者要求目标暴露无障碍树。两种的适用面都明显窄于前台，
   细节见上文对应两节。
2. **游戏 / DirectX / 部分 UWP 无效**：这些程序绕过标准输入队列。
3. **管理员权限**：若目标程序以管理员运行，Windows 的 UIPI 会**静默丢弃**本工具注入的点击
   （表现为「点了没反应」）。此时必须以管理员身份运行本工具。
4. **杀软误报**：输入注入天然敏感，打包分发时建议做代码签名。
5. **焦点抢占**：Windows 的 Foreground Lock 可能阻止程序主动激活目标窗口，
   本工具不做强制抢焦点，请手动把目标窗口切到前台。
6. **纯按键步骤需要目标窗口处于前台**：鼠标点击靠坐标命中窗口，而前台注入的按键是发到焦点窗口的。
   （后台模式下按键投给绑定窗口；UIA 模式下的按键同样**回落到前台注入**——两者的键盘都比鼠标
   更不可靠，很多程序会忽略。）
7. **录制不产生「条件步骤」**：录制只能记录「什么时候做了什么」，记不下「等某个按钮出现再点」。
   目标界面加载变慢时，回放就会点空——这时候用「**+ 找图**」手动补一个等待步骤。
8. **找图是原尺寸、逐像素的精确匹配**：目标程序换主题、换语言、改 DPI 缩放之后，
   原来截的模板就失效了，必须重新截。参数里的「容差」只能容忍文字抗锯齿级别的细微差异。
9. **找图是全屏搜索，不限定区域**：每轮都要抓一整帧虚拟桌面。在小屏幕上无所谓，
   4K 多屏下建议把「轮询间隔」调大一些（每帧约 50ms 的抓屏开销）。
10. **找图要求目标真的显示在屏幕上**：被其它窗口完全挡住、最小化、翻到后台标签页里都找不到
    （找图是抓屏比对，抓到的只是可见像素）。UIA 模式同理——它是按**屏幕坐标**取控件的，
    所以目标被挡在下面时要么取到遮挡者的控件（绑定过窗口就会被那层校验拦下），要么取不到。
    本工具不做「不看屏幕、直接在控件树里搜按钮」的定位（那属于后续计划）。
11. **找图不适合追动画/渐变**：模板需要有一段稳定的纯色区域才稳。纯色区域太小时对话框会给出橙色提示。
12. **超时快照只在「停止并报错」模式下生成**：如果是「继续下一步」，一个循环里反复超时的等待步骤
    会写出一堆几乎一样的图，反而把有用的那张埋掉——那种情况请看日志里的「最接近的相似度」。
13. **录制期间无法操作本工具之外的窗口切换**：屏蔽输入模式下所有鼠标键盘都被吃掉，
    这是设计如此，用 F10 结束即可。
14. **UIA 模式只点得动「有 Invoke 语义」的控件**：按钮、链接、菜单项、列表项可以；纯文本和空白
    区域不行。而且目标必须暴露无障碍树（Swing/AWT 要 `jabswitch -enable` **且**开 IDEA 的
    `Support screen readers`，改完重启）。右键/中键、移动鼠标、按键在 UIA 里没有对应语义，
    会**回落到前台注入**——所以「UIA 不占鼠标」指的是左键点击。

## 测试

四套测试，按「跑起来需要什么」分开：

```powershell
python tests\test_smoke.py           # 141 个用例，需要 PySide6；只认 Windows（app\win\* 在 import 阶段就要绑 DLL）
python tests\test_win_integration.py # 18 个用例，只认 Windows（其它平台自动 skip）
python tests\test_probe.py           # 52 个用例，零依赖，任何平台都能跑
python tests\test_uia.py             # 82 个用例，零依赖，任何平台都能跑（其中 4 个真 COM 用例只认 Windows）
```

`test_smoke.py` 使用 Qt 的 `offscreen` 平台插件，不会真的弹窗，也不会真的点鼠标
（引擎测试使用 `FakeBackend` + 注入的假抓屏函数，并校验完整事件时间线）。
`test_win_integration.py` 反过来：**真的建窗口、真的投消息**，细节见本节末尾。
`test_probe.py` 测的是**探针的判定规则**——那部分是纯函数，所以它反过来是唯一一套
连 PySide6 都不需要的测试（`probe_background.py` 对 `ctypes.WinDLL` 做了保护，
非 Windows 上依然能 import）。把「JCEF 判成能后台点」这类会把用户带沟里的结论钉死在用例里。
`test_uia.py` 测的是 **UIA 后端本身**：GUID 与**整张虚表下标**、HRESULT 翻译、`ElementInfo`、
点击与父链上溯、指针释放、进程校验、回落、按线程持有 COM，以及 **COM 调用层自己**——
虚表解引用、`c_void_p` 与函数地址的转换、出参指针的收发。最后这一层用**假 COM 对象 +
真回调**端到端跑起来（不是断言几个数字）：因为那一层写错不会报错，只会读到野指针然后
**段错误**，是最难查的一类故障。它特意做成「非 Windows 也能 import、也能跑这些逻辑」——
COM 那层对 `WinDLL` 做了保护，假客户端顶掉真实 UIA 调用，只有真的要碰系统的那 4 个
用例才 skip。

四套都在 CI 上跑（`.github/workflows/windows.yml`），另外还多一个 job
校验 `bootstrap.py` 的内嵌快照与仓库**逐字节一致**——改了文件忘记 `--sync` 是这套
「一个文件就是一个项目」的设计特有的失效模式，交给 CI 守着比靠记性可靠。

CI 分四个 job 也是按同一原则：`static`（ubuntu）跑探针判定与 UIA 的**纯逻辑**；
`integration`（windows）跑真实窗口集成测试，**外加 `test_uia.py` 里那 4 个真 COM 用例**
（手写的虚表下标只有真的调一次才能证明没写错）；`smoke`（windows，需要 PySide6）跑界面那套；
`build`（windows）**把 exe 真的打出来**——它跑的就是用户双击的那个 `build.bat`（所以那几套
测试在这里跑了第二遍，换来的是「用户拿到的那条路径」被真的走一遍），打完之后还会**把 exe
真启动一次**：等它写出日志、打出全文、`ERROR` / `CRITICAL` 一律判负（进程活着不等于装配
没问题，出错被吞掉、降级继续跑也是一种失败），最后把产物传成 artifact 供下载。
runner 是无头环境，所以启动日志里那条「系统托盘不可用」的 WARNING 是**预期的**——
托盘按设计退化成空壳，真机上有托盘时走另一条分支。
覆盖：

- `INPUT` 结构体大小与联合体内存共享语义

- 录制整条链路：F11 开始 → F10 结束 → 替换 / 追加 / 丢弃 / 空录制 /

- 主窗口 / 步骤编辑器 / 编辑对话框的装配，以及「拾取坐标」的隐藏与恢复流程
  （含「F8 改写移动轨迹终点」「延时步骤拒绝取点」）
- 找图界面：`+ 找图` 按钮、模板预览与纯色提示、没截模板时不让点「确定」、
  拖框时对话框让开、模拟测试的命中 / 落空两种文案
- `PickCoordinator` 的第二种取法：拖框截模板、截取失败时发 `failed` 并让调用方收尾、
  `busy` 覆盖「遮罩已隐藏但截取还没完成」的窗口期、取点与截模板互斥
- 现场快照：PNG 通道顺序（BGRA 必须按 RGB32 解读，否则画面整体偏色）、
  只保留最近 N 张、落盘失败绝不打断宏
- **后台点击**：`lParam` 的客户区坐标打包（含负坐标截断）、按键 `lParam` 的扫描码与抬起标志、
  点击的 `move/down/up` 消息序列与左右键分支、命中点投给最内层子窗口、绑定时归一化到顶层窗口、
  失效句柄拒绝绑定、未绑定时按坐标兜底找窗口、找不到目标时不投递且只警告一次
- **UIA 后端**（`test_uia.py`）：GUID 字面量与 COM 二进制布局、**整张虚表下标逐条比对**、
  HRESULT 的翻译、`ElementInfo.describe()`、坐标取控件 → `Invoke`、
  点在按钮内层文本节点时**往上找到可 Invoke 的祖先**（且中间层恰好释放一次）、
  找不到时只告警**不擅自回落**、控件不属于绑定进程时跳过、未绑定时不校验、
  右键/中键/移动/按键各回落一次、COM 客户端按线程持有且失败结果也缓存、
  非 Windows 上优雅地「不可用」而不是崩溃
- **COM 调用层本身**（`test_uia.py`）：用假 COM 对象 + **真回调**把 `_call` 真的调起来——
  接口指针要**解两层**才到函数地址（少解一层读的是虚表指针本身，实测 ``0xfd010303`` 这种
  垃圾地址，一调就崩）、虚表空槽与空对象被挡在调用之前、返回值原样返回、
  出参指针的收发（坐标进去、控件指针出来）、`TreeWalker` 取一次就缓存而失败不缓存、
  `Element` 的每个属性都按各自的出参类型走一遍（``BSTR*`` / ``int*`` / ``BOOL*`` /
  ``RECT*`` / 句柄——类型写错不会报错，只会静默写坏内存），BSTR 必须被 `SysFreeString` 放掉，
  以及完整的「取图案 → `Invoke` → 放图案」调用链
- **真 COM 自检**（`test_uia.py` 的 `TestRealUia`，仅 Windows / CI 的集成 job）：
  在真实桌面上走一遍 `CoCreateInstance → ElementFromPoint → 读 Current* 属性 →
  GetParentElement → GetCurrentPattern`——虚表下标写错的唯一可靠探测器
- 拆分出来的子系统：托盘菜单转发（`QAction.triggered` 捎带的参数要被丢掉）、
  无托盘时的降级、录制落地的替换/追加语义、日志 handler 的成对挂载与摘除
- **真实窗口上的后台点击**（`test_win_integration.py`）：自造带 `WndProc` 的顶层窗口 + 子窗口，
  验证客户区↔屏幕坐标往返、命中点下钻到最内层子窗口、不可见与 `WS_EX_TRANSPARENT` 子窗口被穿透、
  点击真的由目标窗口收到（`WM_MOUSEMOVE → 按下 → 抬起`，`lParam` 是正确的客户区坐标）、
  右键分支、只投 `WM_MOUSEMOVE` 的移动、后台键盘的按键与扫描码、按点绑定归一化到顶层窗口、
  失效句柄拒绝绑定
- **探针的判定规则**（`test_probe.py`）：框架类名表（Chromium / Swing / Qt / WPF / WinForms /
  UWP / WinUI / 经典控件 / 认不出）、**Chromium 压过外层框架**、几路证据合议出的每条路线与置信度、
  **UIA 实测把结论提级（确实通了）或降级（没动静）**、`UiaProbe.viable` 只认「找到了能 Invoke
  的控件」、判不出来时退回前台、结论必须给理由、截图区域在屏幕内被正确夹取（含负原点多屏）、
  模板质检（纯色 / 两种色 / 99% 单色 → 差）、挪开光标的落点不越界，
  以及最要紧的一条：**生成的方案能被 `Profile.from_dict()` 读回并通过 `validate()`**

`SendInput` 注入与 GDI 抓屏这两层不做自动化断言，改为真机联调验证（抓一帧 → 抠一块当模板 →
必须一次命中且坐标精确、通道差为 0）。

后台点击和 UIA 则是**分层都测**：`test_smoke.py` 把 `post_message` / 窗口查询函数换成假的，
断言「逻辑上发给谁、发什么消息、坐标换算对不对」；`test_win_integration.py` 在**真实的** Win32
窗口上把整条链路跑一遍——消息真的投出去、真的由目标窗口的 `WndProc` 收下；`test_uia.py` 用
假客户端把 UIA 的逻辑（父链上溯、指针释放、进程校验、回落）测干净，再用 `TestRealUia` 在真机上
把 COM 调用真的走一遍。于是这三层的实现细节在自动化测试里都有断言守着，而不是只能靠肉眼。

真机仍无法被替代的只剩两件事：**目标程序认不认 `WM_*`**、以及**它的无障碍树里有没有那个能
Invoke 的控件**。两者都取决于对方是什么程序，用 `tools\probe_background.py` 跑一次就能拿到
结论（它会自己判定、**实测哪条真的生效**、并生成方案，见「后台点击」一节）；而判定规则本身
是有测试守着的（`test_probe.py`），因为判错方向的代价是让用户拿着一份跑不通的方案来回折腾。

## 打包

双击 `build.bat`（或命令行里跑 `build.bat`）即可。它会按顺序做四件事：
先跑一遍测试——**冒烟（`test_smoke.py`）、探针判定（`test_probe.py`）、UIA 后端（`test_uia.py`）**
三套（**任何一套不过就不打包**，避免打出一个坏 exe），清掉旧的 `build\`、`dist\`，
再调 PyInstaller，最后报告产物路径与体积。
（真实窗口那套 `test_win_integration.py` 不在这里跑：它要真的建窗口，本地打包时窗口会闪；
CI 的 `integration` job 专门跑它。）

产物：`dist\AutoClicker.exe`，单文件、无控制台窗口。

> 不想在本机装 PyInstaller 的话：CI 每次推送到 `main` 都会打一次包，产物作为
> **`AutoClicker-exe`** artifact 挂在运行记录里，可以直接下载（保留 14 天）。详见「测试」一节末尾。

```powershell
:: 需要先装 PyInstaller（build.bat 会检查并提示）
pip install pyinstaller
build.bat
```

等价的裸命令就是：

```powershell
pyinstaller --noconfirm --onefile --windowed --name AutoClicker main.py
```

注意点：

- 裸命令**不带 Qt 裁剪**，产物明显偏大。`build.bat` 里额外排除了 Qml / Quick / WebEngine /
  Multimedia / Charts / Sql 等本工具用不到的 Qt 子系统——PySide6 每个模块都是独立的 DLL，
  这才是体积大头（`--exclude-module` 能把对应的 DLL 一起拦掉）；
- 把 `AutoClicker.ico` 放在项目根目录，`build.bat` 会自动 `--icon` 带上它。不提供也没关系：
  窗口与托盘图标本来就是 `app/ui/icon.py` 代码画的，只是 exe 文件本身会显示 PyInstaller 的默认图标；
- 图标用代码绘制，因此没有 `--add-data` 的资源路径问题；找图模板存在方案 JSON 里，
  也没有额外的图片文件要打包；
- 若需要开机自启或写入程序目录，建议在 `build.bat` 里加 `--uac-admin`，或改用运行时按需提权；
- 单实例锁使用 `Local\` 命名空间，同一用户会话内唯一；
- 方案文件放在 `%LOCALAPPDATA%`，因此升级 exe 不会丢配置；
- `build.bat` 必须保持 **CRLF** 行尾：cmd.exe 解析多行 `if (` / 续行 `^` 时依赖它，换成 LF 会错乱。
  它的输出文案也刻意全部保持 ASCII，因为中文 Windows 的控制台默认是 GBK 代码页，
  混入非 GBK 字符会直接 `UnicodeEncodeError`。

## 从零重建项目（bootstrap.py）

`bootstrap.py` 把整份项目（52 个文件）硬编码在自己内部，不读任何原始文件就能还原出完整项目，
适合打包分发「一个文件就是一个项目」：

```powershell
python bootstrap.py D:\some\where\auto-clicker
python bootstrap.py            :: 不传参数 → 当前目录下的 auto-clicker\
```

- 目标目录非空时会列出后果并让你输入 `yes` 确认，确认后**清空**该目录再生成；
- 若目标目录里存在 `bootstrap.py`（说明指向了源码仓库本身，删掉就找不回来了），脚本直接拒绝执行；
- 生成的 `build.bat` 会保留 CRLF 行尾。

改了 `app/` 下的源码后，跑一次 `--sync` 刷新内嵌快照，避免快照与源码漂移：

```powershell
python bootstrap.py --sync
```

`--sync` 只按 `FILES` 里已有的键刷新内容，不自动增删文件；若仓库里出现了没登记的 `.py`，
它会打印 `[WARN]` 提醒——不然生成的快照会在 `import` 阶段才炸，那种报错不好查。
